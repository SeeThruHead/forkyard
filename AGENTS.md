# Working in this repository

## No AI attribution

Never add AI or agent attribution to anything in this repository: no co-author trailers naming a tool or model, no "generated with" or "generated by" lines, no robot emoji, in commits, files, docs or package metadata. Lefthook's commit-msg hook (`lefthook.yml`, installed by `pnpm install`) rejects such commit messages, and `test/Attribution.test.ts` fails if any tracked file or commit contains them.

## Commands

`just` lists everything. `just setup` installs dependencies and git hooks, `just check` runs format, lint, typecheck and tests, `just daemon` runs forkyard, `just tour` runs the example tour. Each recipe calls a package script, so there is one definition of each command.

## Platforms

macOS and Linux. Windows is supported through WSL, which is Linux; native Windows stops at startup with a pointer to WSL. Everything that differs between operating systems lives in `src/platform/Os.ts` as one service with a layer per OS.

## What the linter enforces

`pnpm run lint` runs oxlint with the project rules in `lint/forkyard.js`:

- `scoped-processes` (error): only `src/Proc.ts` and the platform layer (`src/platform/Os.ts`) may start processes (`node:child_process`, `effect/process`, `NodeServices`), only the platform layer may call `process.kill` (the Registry's reaper goes through it), and `Effect.run*` is not called inside the daemon: effects are composed and run once at the entry point.
- `no-gen-wrapper` (warning): a named function that only returns `Effect.gen` is usually better as `Effect.fn` (named and traced) or `Effect.fnUntraced`.

## What reviewers check instead

These need judgment, so they are not lint rules.

- Resources live in scopes. Anything acquired and released (processes, containers, routes, database rows that track a process, exporters) is acquired with a release in a scope. Fibers that only do work in forkyard's own memory do not need one.
- Branded types for values that are not really strings or numbers: ids, names that become hostnames, ports, pids, paths. Use the schemas in `src/Ids.ts` and their smart constructors; add one there before passing a bare `string` or `number` around.
- Single level of abstraction. A function reads at one level: an orchestration step calls named steps and does not also build SQL, parse ports or format strings inline. This is about what a function mixes, not how long it is.
- Service methods stay small enough to read in one screen. Split by responsibility, not to hit a number.

## The public protocol

The tray app, the terminal UI, the dashboard and other tools talk to the daemon through the RPCs in `src/Protocol.ts`. The public ones are listed in `test/Protocol.test.ts` (`Info`, `Status`, `Usage`, `Up`, `Down`, `Restart`, `Runs`, `RunLog`, `Env`, `DaemonLogs`, `Logs`). Clients may be older than the daemon, so:

- Public RPCs and their fields are only ever added to. Never remove or rename an RPC or a field, and never change what a field means.
- New fields on anything a client reads are optional, so older daemons' messages still decode.
- `protocolVersion` in `src/Package.ts` goes up only when a client starts needing something an older daemon lacks. Clients refuse daemons with a lower protocol and say to restart the daemon.
- When `protocolVersion` goes up, capture that protocol's `Status`, `Usage` and `Info` messages into `test/protocol/v<n>/`, with paths replaced by `/home/dev/...`. Every older fixture must keep decoding.
